# Deployment Pipeline Operations Runbook

## Purpose

This runbook covers the operator steps that cannot be fully automated until the live Neon, Blob, and OpenAI credentials exist. It keeps the production/staging setup explicit and preserves the manual promotion gate approved for Recetas.

## Live Resource Setup

### Production

- Create or connect the Neon production database for `recetasfamilia.app`.
- Apply the clean Postgres baseline schema generated by `npm run db:postgres:check`.
- Do not seed sample data into production.
- Create or connect the production Vercel Blob store.
- Use a production-only OpenAI API key.
- Generate a unique production `JWT_SECRET`.

### Staging

- Create or connect the Neon staging database for `staging.recetasfamilia.app`.
- Apply the same clean Postgres baseline schema.
- Seed staging with sample data only.
- Create or connect the staging Vercel Blob store.
- Use a staging-only OpenAI API key.
- Generate a unique staging `JWT_SECRET`.

### Preview

- Use one isolated Neon branch or database per PR before treating a preview as production-like.
- Use preview-only Blob prefixes or preview-only Blob stores.
- Keep OpenAI-backed import/OCR disabled by default.
- Enable OpenAI only for a specific preview when testing requires it, then remove the preview key after validation.
- Clean up preview Neon and Blob resources when the PR closes.

### Secret Intake Checklist

Collect these values outside the repo before running `vercel env add`. Keep the production and staging values separate.

- Production Neon `DATABASE_URL`
- Staging Neon `DATABASE_URL`
- Production Vercel Blob `BLOB_READ_WRITE_TOKEN`
- Staging Vercel Blob `BLOB_READ_WRITE_TOKEN`
- Production OpenAI `OPENAI_API_KEY`
- Staging OpenAI `OPENAI_API_KEY`
- Production `JWT_SECRET`
- Staging `JWT_SECRET`

Generate each `JWT_SECRET` as a long random value, for example with `openssl rand -base64 48`. Do not reuse the same value between production and staging.

## Staging Validation

Run this after staging environment variables are configured and the `pre-main` deployment has been redeployed.

- Confirm `https://staging.recetasfamilia.app/api/health` returns `200` and `status: "healthy"`.
- Confirm the homepage loads at `https://staging.recetasfamilia.app`.
- Confirm login and register routes load.
- Confirm authenticated recipe list and recipe detail pages load.
- Upload a recipe image and confirm it can be read back through the app route.
- Import a standard recipe document and confirm the parsed draft can be reviewed.
- Import a handwritten recipe sample and confirm OpenAI OCR is used in staging.
- Inspect Vercel deployment logs for build warnings or failed functions.
- Inspect Vercel runtime logs while running the smoke checks.
- Review Neon and Blob dashboards for unexpected usage.
- Record the staging validation result in the PR or release notes before promotion.

## Manual Production Approval

Promotion from `pre-main` to `main` stays manual.

1. Confirm GitHub required checks pass on `pre-main`.
2. Complete the staging validation checklist.
3. Add a GitHub-visible approval comment or release label.
4. Merge or promote `pre-main` to `main`.
5. Let Vercel deploy production from `main`.
6. Run production post-deploy validation.

## Production Post-Deploy Validation

- Confirm `https://recetasfamilia.app/api/health` returns `200` and `status: "healthy"`.
- Confirm the homepage loads.
- Confirm login and register routes load.
- Confirm authenticated recipe list and recipe detail pages load.
- Confirm image routes read from Blob through the app route.
- Confirm import routes are available when authenticated.
- Inspect Vercel build logs and runtime logs.
- Review Neon, Blob, and OpenAI usage after validation.

## Log Review

### Build and deploy logs

- Open the Vercel project `recetas`.
- Select the latest deployment for the target environment.
- Review build logs for failed install, Prisma generation, build, or routing steps.
- Review deployment summary for the assigned domain or alias.

### Runtime logs

- Open the Vercel project `recetas`.
- Use the deployment or project runtime logs filtered by the production or staging domain.
- Check `/api/health`, auth routes, recipe routes, upload routes, and import routes during smoke testing.
- Treat repeated `5xx` responses, Prisma connection errors, Blob token errors, or OpenAI API errors as blockers before promotion.

## Rollback

Rollback is for production incidents after a `main` deployment.

1. Open the Vercel production deployment list for `recetas`.
2. Identify the last known-good production deployment.
3. Use Vercel Instant Rollback to restore that deployment.
4. Confirm `https://recetasfamilia.app/api/health` returns healthy.
5. Confirm the homepage, login route, and recipe list load.
6. Inspect runtime logs for continuing errors.
7. Create a fix branch from `pre-main` or revert the problematic change through the normal branch flow.

Application rollback does not roll back database migrations or Blob object changes. Any production schema migration must have a forward-fix or rollback note before promotion.
